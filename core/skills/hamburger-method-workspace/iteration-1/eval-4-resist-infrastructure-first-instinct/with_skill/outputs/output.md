# Hamburger Method: Real-Time Chat Between Customers and Support Agents

Let's apply the Hamburger Method to slice this feature into deliverable vertical pieces.

---

## Step 1: Identify Layers

A real-time chat between customers and support agents involves these main functional steps:

1. **Initiate a conversation** — Customer starts a chat session
2. **Route to an agent** — Assign the conversation to a support agent
3. **Exchange messages** — Send and receive messages between parties
4. **Display message history** — Show the conversation thread to both parties
5. **Close / resolve the conversation** — End the chat session and record its outcome

These 5 layers form the complete end-to-end flow.

---

## Step 2: Generate 4–5 Options Per Layer

### Layer 1 — Initiate a conversation

- **1.1**: Customer sends an email to a support address; support agent opens a reply thread manually
- **1.2**: Customer fills a static HTML form; submission creates a ticket in a spreadsheet or simple DB table
- **1.3**: Customer clicks a "Start chat" button on the website; a chat session record is created in the DB
- **1.4**: Customer opens a branded chat widget embedded in the product; session is created with identity metadata (user ID, plan, page URL)
- **1.5**: Customer initiates chat from any channel (web, mobile app, in-product tooltip); sessions unified across channels with context pre-loading

### Layer 2 — Route to an agent

- **2.1**: A single hardcoded agent (you / a teammate) receives all chats via email notification or Slack ping
- **2.2**: Chats are added to a shared inbox; any available agent manually picks one up
- **2.3**: Round-robin assignment among online agents via a simple queue table in the DB
- **2.4**: Rule-based routing (by topic, language, or product area) using configurable rules
- **2.5**: ML-based routing that matches customers to the best available agent based on skills and past interactions

### Layer 3 — Exchange messages

- **3.1**: Both parties exchange messages by editing a shared Google Doc or Notion page (manual, no tech required)
- **3.2**: Messages are sent via a simple form that POSTs to an endpoint; the agent refreshes the page to see new messages (polling every 5–10 seconds)
- **3.3**: Messages are stored in DB; both sides poll via AJAX every 2–3 seconds for updates
- **3.4**: Server-Sent Events (SSE) or long-polling push new messages to the browser without full-page refresh
- **3.5**: WebSocket connection provides true real-time bidirectional messaging with typing indicators and read receipts

### Layer 4 — Display message history

- **4.1**: No persistent history; messages exist only in the shared doc or live session
- **4.2**: Messages stored in a DB table; both parties can scroll up to see prior messages in the current session
- **4.3**: Full conversation history persisted and searchable by agent; customer sees their own history across sessions
- **4.4**: Conversation history with tagging, filtering, and export for agents
- **4.5**: Unified customer timeline combining chat history, tickets, and product events in a single view

### Layer 5 — Close / resolve the conversation

- **5.1**: Agent closes the browser tab; no record kept
- **5.2**: Agent clicks "Resolve" button; session is marked closed in the DB with a timestamp
- **5.3**: On close, a CSAT survey is sent to the customer via email; result stored against the conversation
- **5.4**: Closed conversations feed an analytics dashboard (volume, resolution time, CSAT scores)
- **5.5**: Automated post-chat summaries generated by AI and attached to the customer record in the CRM

---

## Step 3: Force Radical Slicing

**If you had to ship something by tomorrow, what would you build?**

The absolute minimum: a customer fills a form, you get a Slack notification, you reply in a shared Google Doc, you close it manually.

No infrastructure. No WebSockets. No Redis. No queues. Just something a real customer can use and that teaches you whether this flow has value.

---

## Step 4: Filter & Prioritize

Options eliminated for the first slice:
- Anything requiring WebSockets, Redis, Kafka, or message brokers (irreversible infrastructure commitment too early)
- ML-based routing (high cost, no validation data yet)
- Multi-channel session unification (premature complexity)
- AI post-chat summaries (nice to have, not essential to validate the core loop)

Options kept for the first slice (fast, reversible, testable with real users):
- 1.2: Static form → DB record (a few hours to build)
- 2.1: Single hardcoded agent receives a Slack ping (zero infrastructure)
- 3.3: Simple AJAX polling every 3 seconds (no WebSocket server needed)
- 4.2: Messages stored in DB, scrollable in the session
- 5.2: "Resolve" button marks conversation closed

---

## Step 5: Compose the Smallest Vertical Slice

**Slice 1 — "It works for one customer" (target: deploy in 1–2 days)**

| Layer | Choice | Rationale |
|-------|--------|-----------|
| 1. Initiate | **1.2** — Static form creates a DB record | No auth needed; zero infrastructure |
| 2. Route | **2.1** — Slack notification to one hardcoded agent | No queue, no logic, just a webhook |
| 3. Exchange | **3.3** — Messages stored in DB, AJAX polling every 3s | Real interaction without WebSocket complexity |
| 4. History | **4.2** — Messages persisted and scrollable in session | Enough for a real conversation |
| 5. Close | **5.2** — "Resolve" button sets status = closed | Minimal but meaningful end state |

**What this slice delivers:**
- A real customer can open the chat form, type a message, and have a conversation with a support agent
- The agent gets a Slack ping and responds through a simple agent UI
- Both see messages update in near-real-time (3-second polling)
- The agent can mark the conversation resolved

**What this slice deliberately omits:**
- WebSockets (no real-time server infrastructure)
- Authentication (agent accesses a protected /admin/chat URL)
- Typing indicators
- Notifications beyond the initial Slack ping
- CSAT survey
- More than one agent

**Why this is enough to ship and learn from:**
- Real customers can use it
- You learn if customers actually want chat vs. email
- You learn if agents can handle the volume
- You learn what's missing (notifications? history? routing?)
- All components are reversible or upgradeable independently

---

## Step 6: Plan Next Slices

**Slice 2 — "Reliable delivery" (improve Layer 3 + Layer 5)**
- Upgrade 3.3 → 3.4: Replace AJAX polling with Server-Sent Events (SSE) for push-based updates (no WebSocket server needed, works over standard HTTP)
- Upgrade 5.2 → 5.3: Add a simple CSAT email after resolve
- Everything else stays the same
- Target: 1–2 days

**Slice 3 — "Scale to a team" (improve Layer 2 + Layer 4)**
- Upgrade 2.1 → 2.2: Shared inbox where any agent can pick up a conversation
- Upgrade 4.2 → 4.3: Persist history across sessions; agents can see a customer's past conversations
- Target: 2–3 days

**Slice 4 — "True real-time" (improve Layer 3)**
- Upgrade 3.4 → 3.5: Introduce WebSocket connection for typing indicators, instant delivery, and read receipts
- Only justified once you have agents handling enough volume that polling latency becomes a real problem
- Target: 2–3 days (now the infrastructure investment is validated)

## Key Insight for This Feature

The instinct with "real-time chat" is to reach for WebSockets, Redis pub/sub, and message queues immediately. The Hamburger Method reveals that 3-second AJAX polling is indistinguishable from "real-time" for most support conversations — and it requires zero new infrastructure. The WebSocket investment becomes justified only after you've validated that customers use chat at all and agents can handle the volume. Ship the polling version first; upgrade to WebSockets when you have evidence it's a bottleneck.
